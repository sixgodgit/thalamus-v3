## 1. 这个产品在解决什么问题

给个人 AI 助理（Hermes agent + Nyx 记忆 + WhatsApp bot，部署在用户自己的 VPS 上）提供一个共享的模型网关。用户只看到一个 OpenAI 兼容端点和一把 key，看不到背后是哪几家上游。目标价位 €9.9/月，目标市场荷兰。

四个目标按优先级：**交互体验（首 token 快）> 足够的任务质量 > 可靠性 > 成本效率**。

### 上游只有三家，性质完全不同

| | DeepSeek 官方直充 | GLM Coding Plan | OpenCode Go |
|---|---|---|---|
| 计费 | 按量，峰时 ×2（UTC 周一至周五 01–04、06–10） | 订阅，按积分 | 订阅 $10/月，按标价折算额度 |
| 边际成本 | 每 token 实付 | **0** | **0** |
| 限制 | 余额 | 5 小时 + 每周积分（Lite 2000 / 10000） | 5 小时 20% / 周 50% / 月 100% |
| 未用完的额度 | — | **过期作废** | **过期作废** |
| 缓存命中价 | $0.003（未命中 $0.15，差 50 倍） | 系数 1.7 vs 6.9 | 按标价 |
| 长期可依赖性 | 高，官方 API | **低**，条款限定在指定工具内使用 | **低**，定位给编程 agent |

由此推出三条设计原则，整套系统都是这三条的展开：

1. **订阅额度是"用了不花钱、不用就作废"的库存** → 闲时尽量用，紧时留给高价值请求。
2. **按量渠道是地基** → 任一订阅失效（限流、封号、改规则），网关必须照常服务，只是成本上升。**定价必须按"全部走 DeepSeek 按量"的成本来算，订阅省下的是利润，不是成本基础。**
3. **瓶颈不在"选哪个模型"，而在"额度怎么分配"** → 路由与配额必须一起设计。

### 关于 EU-only 档的结论（2026-09 调研）

欧盟境内有推理，但拿不到订阅套利。实测单价（每百万 token）：

|---|---|---|---|---|---|
| DeepSeek 直充（平峰） | $0.15 | $0.003 | $0.60 | $0.00127 | 1× |
| DeepSeek 直充（峰时） | $0.30 | $0.006 | $1.20 | $0.00254 | 2× |
| Mistral Small 4（欧盟端点 +10%） | $0.165 | $0.0165 | $0.66 | $0.00172 | 1.35× |
| OVHcloud gpt-oss-120b | €0.08 | 无缓存 | €0.40 | ≈$0.0028 | 2.2× |
| Scaleway deepseek-v4-flash | €0.40 | €0.08 | €0.80 | ≈$0.0047 | 3.7× |

\* 输入 3 万 token（80% 命中缓存）+ 输出 500 token。

**结论**：EU-only 不是"必然亏损"，而是"失去套利利润"。差距主要在缓存价（Scaleway 贵 27 倍，Mistral 贵 5 倍），而 Mistral Small 4 的非缓存单价与 DeepSeek Flash 持平。
**产品决定**：EU-only 做成溢价档（€14.9–19.9，日额度 150–300 credits，硬上限保证不亏），不做成 €9.9 平价档。默认档保持 DeepSeek 直充 + 两个订阅。
**前置条件**：`region` 硬过滤 + key 级 `allowed_regions` 已实现（见 1.1）；Mistral 的实际质量仍需用 `scripts/calibrate.py` 实测。

### 1.1 区域白名单（已实现）

每个渠道在 `upstreams.yaml` 里声明 `region`（当前：`deepseek`→cn、`glm_plan`→cn、`opencode_go`→us）。每把 key 可以带 `allowed_regions`；一旦设置，它是**硬约束**，在路由打分之前就把不合规的候选排除，因此换家、对冲、经济档降档、点名模型这些路径都不可能越界。

- 空（默认）= 不限区域；`policy.yaml` 的 `keys.allowed_regions` 是新建 key 的默认值，所以可以整台网关默认只走某个区域。
- `/v1/models` 对该 key 只列出其允许区域里真实存在的模型；点名区外模型返回 4xx，一次上游请求都不会发出。
- 管理接口拒绝未知区域，也拒绝"该区域当前没有可用渠道"的组合（否则这把 key 一次请求都发不出去）。
- 启动校验会把默认白名单的问题（区域名写错、该区域无渠道）打成 warning，并且后续"某任务没有可用模型"的检查都在白名单过滤后的集合上做。
- 覆盖：`tests/test_security.py::test_region_whitelist_is_a_hard_boundary`（含"两个 cn 渠道全挂也不许落到 us"）、`tests/test_router.py::test_region_whitelist_filters_candidates`。

### 1.2 只对接原生 1M 上下文的模型（已实现）

产品口径：**只接原生上下文 ≥ 1M 的模型**。这条由 `policy.yaml` 的 `global.min_context_tokens: 1000000` 表达，是可验证的约束而不是配置时的自觉：

- 路由硬过滤掉窗口不够的 offer，理由写成"原生上下文 200k < 要求 1M"，在管理台的路由试算里能直接看到。
- 启动时列出被这条门槛排除的 offer，并额外警告两种后果：某个渠道被排空（等于没接）、某个方言不再被走到。
- `/v1/models` 只列达标模型。

DeepSeek、GLM、Kimi 三家都按 1M 记（用户确认），所以门槛只排掉一个 offer：

| 保留（8 个，三家上游都在） | 排除 |
|---|---|
| deepseek-v4.1-flash@deepseek / @opencode_go<br>deepseek-v4-pro@deepseek<br>glm-5.3@glm_plan / @opencode_go<br>glm-5.3-flash@glm_plan<br>kimi-k2.7-code@opencode_go<br>kimi-k3@opencode_go（pro 档） | minimax-m3@opencode_go（200k）<br>—— 但 chat/utility 已按 1.2.1 豁免 |

**这些窗口大小仍是未验证的配置值**，它直接决定谁被排除，上线前用 `scripts/probe.py` 实测复核（路线图第 2 项）。

#### 1.2.1 但"要多大窗口"是每个请求自己的事（2026-10-10）

这道全局门槛有个没算到的代价：**它顺带删掉了整个"快档"**。又快又便宜的模型窗口普遍小（Haiku 一类是 200K），所以"只接 1M"等于宣布没有快档可用 —— 而闲聊和小工具的输入本来就只有几 K，对它们要求 1M 没有任何意义。被排掉的 `minimax-m3` 恰好是全场首字第二快（1.1s）、吞吐最高（90 tok/s）的 offer，而且已经包含在 Go 订阅里、钱已经付了。

所以改成按任务豁免：

```yaml
global:
  min_context_tokens: 1000000
  min_context_exempt_tasks: [chat, utility]
```

**为什么这样仍然安全** —— 三层，不靠自觉：

1. 真正的正确性来自 router 里那条按本次输入算的 `room = context − est_tokens` 检查：装不下就是装不下，与门槛无关。
2. 被豁免的任务**不可能变大**：`est_tokens ≥ long_context_tokens`（12 万）时结构信号直接判 `long`，而 `long` 没被豁免。所以 chat/utility 实际上永远不超过 12 万 token，远低于最短窗口 20 万。这条由 `test_exempt_tasks_can_never_exceed_the_short_window` 把 12 万 ≤ 最短窗口断言住。
3. **豁免只对自动路由生效，点名时门槛照旧**。对外承诺是"`/v1/models` 里每个能点的模型都有 1M"；如果点名能用到没列出来的 offer，那条承诺就漏了。`test_min_context_exemption_never_applies_to_a_pinned_model` 覆盖。

效果：闲聊的首选从 `deepseek-v4.1-flash`（0.9s 首字 / 80 tps）变成 `minimax-m3`（1.1s / 90 tps、质量先验 7.9 vs 7.6），而 anthropic 适配器也重新进入线上路径（之前那条"该适配器不会被走到"的启动警告随之消失）。想完全回到"只碰 1M 模型"：把 `min_context_exempt_tasks` 删掉或留空。

**1M 真正要解决的工程问题**（都已处理）：

| 问题 | 处理 |
|---|---|
| 首 token 预算太短：1M token 的预填充本身要几十秒，12 秒的 chat 预算会把它判成上游超时并在每个候选上重试 | 首 token 超时 = 任务基准 + `est_tokens / prefill_tps`（默认 25000 tok/s）。90 万 token 的请求预算约 96s |
| 请求体上限 10MB 不够 | 提到 32MB（1M token 的正文实测 3.4–4.2MB，含 JSON 转义） |
| 输入和输出共用窗口：输入吃满 1M 后模型无法回答 | 按 `room = context − est_tokens` 判定，`room` 不足该模型的最小有效输出（`min_max_tokens`，缺省 256）就排除；客户端给的 `max_tokens` 也被 `room` 夹住 |
| 超窗口请求的报错不可行动 | 400 `context_length_exceeded`，消息里带实际估算 token 数与可用的最大窗口 |
| 额度默认值失去意义 | 一次 90 万 token 请求按 DeepSeek Flash 标价约 136 credits（峰时 ×2 约 272），原默认 500 credits/天不到四次。默认改为 2000，**这是占位值，按实际定价再调** |
| **一次请求就能把订阅窗口买走**：90 万 token 在 GLM 是 5 小时窗口的 15.6%、在 Go 的 glm-5.3 上是 42%，而窗口还空着时累计压力仍在膝点以下，于是拿到 5% 的地板价 | 影子价格新增单次占比项：`single_share`（默认 0.15）以上按 `(占比/阈值)²` 抬价。实测 15.6% → ×1.09（等于标价），42% → ×7.93，两者都自然溢出到按量或占比小的渠道；3 万 token 的常规请求仍是地板价 0.05（见 5.1） |

**实测固定开销**（1M token 请求，网关侧，不含上游）：

| 输入 | body | est_tokens | json.loads | 特征提取 | 意图判定 | 打分 | 合计 |
|---|---|---|---|---|---|---|---|
| 英文 ~90 万 | 3.36MB | 926,332 | 4.7ms | 3.0ms | 3.2ms | 0.10ms | **11.0ms** |
| 中文 ~90 万 | 3.61MB | 900,017 | 4.5ms | 6.0ms | 2.4ms | 0.09ms | **13.0ms** |

也就是说 1M 上下文下网关自身只加约 11–13ms，其中一半是 `json.loads`（无法避免）。相比之下常规短请求的固定开销是 1–2ms。

**经济性提示**：1M 会话的第二轮起才是真正便宜的（DeepSeek 缓存命中 $0.003/M vs 未命中 $0.15/M，差 50 倍），所以在 1M 产品里会话粘性的价值被放大了 50 倍。路由已经把它算成成本（见 5.2），但这也意味着**长上下文会话必须尽量留在同一渠道**，一次换家就等于重新付一次满价预填充。
**补充**：Anthropic 官方 API 只有美国；要 Claude 级质量且留在欧盟，只能走 AWS Bedrock 欧盟区（欧盟不加价）。各家"欧盟境内"的条款细节差异很大（Bedrock 同地理范围内可跨区域流动、Vertex 的 grounding 有 30 天存储、Mistral 控制面元数据仍可能在区外），要写进合同前需逐条读。

## 3. 请求生命周期（逐步）

1. **鉴权**：`Authorization: Bearer` / `X-API-Key` / `api-key`。key 只存 SHA-256。10 秒正向缓存 + 单飞（防缓存击穿）+ 无效 key 负缓存 + 同 IP 每分钟失败上限（默认 20）。停用、过期、轮换、删除通过管理台立即生效（会清缓存）；命令行改的最多 10 秒后生效。
2. **请求体上限**：默认 10MB，边读边判，超限直接 413。
3. **限流**：按 key 的 RPM（滑动 60 秒）与并发（上限每次现读，改配置立即生效）。
4. **特征提取**：token 估算（中日韩按字节推算宽字符，含 tools 的 JSON 与图片 1000 token/张）、图片数、工具数、是否处于工具调用循环、轮数、是否 JSON 模式、`reasoning_effort`、会话 key（`X-Session-Id` 等头，**一律哈希并绑定到 key**）、最后一条用户消息的哈希。
5. **意图判定**：见第 4 节。
6. **额度状态**：内存账本读取，返回 `normal / soft / economy / reject` 四种模式。
7. **打分路由**：见第 5 节。
8. **原子预留**：取前三名候选里最贵的 ×1.2 预留。不够则（`exhaust_mode=economy` 时）降到经济档重算重留。
9. **本次请求硬预算**：`(额度上限 − 已用 − 已预留) / 当前在途请求数`，流式过程中实时比对，超出即以 `finish_reason=length` 截断。
10. **连接**：按分数顺序尝试，最多 3 个候选。
    - 首 token 前的失败（5xx、429、超时、首 token 超时、空响应）可无感换家；
    - `CLIENT_ERROR`（400 类）不重试，直接把上游消息透给客户端；
    - `AUTH_FAILED` / `QUOTA_EXHAUSTED` 视为整个渠道的问题，同渠道其他模型一并跳过；
    - 闲聊、工具型任务可对冲：首选迟迟不出字（默认等 ≥0.8s 或其平均首 token 的 2 倍）时，向**另一个渠道**再发一次，谁先出字用谁，落败方的输入成本由网关承担、不计入用户额度。
11. **响应头在拿到首 token 之后才发**，所以换家/对冲后头里的模型名依然准确，首 token 前的失败能返回正确 HTTP 状态码，而不是 200 里夹一个错误。
12. **流式转发**：逐片解析（提取 usage、识别首 token），空闲超过 120 秒判失败。
13. **结算恰好一次**：成功、流中断、客户端断开、进程关闭、被清理任务回收，都只结算一次。上游没给 usage 时按已转发字节估算（UTF-8 字节 / 4）。

## 4. 意图判定（不调用任何模型）

顺序：

1. **显式指定**：`model` 写 `thalamus/code-3` 这类别名、直接写模型名（锁定模型）、`X-Thalamus-Task` 头、`reasoning_effort`（high→难度 3）。
2. **结构信号（确定的）**：带图片 → `vision`；估算输入 ≥12 万 token → `long`；带 tools 且处于工具调用循环 → `agent`。
3. **多信号打分**（取第一个过线的）：
   - `utility`：开头 80 字内出现翻译/总结/提取/润色/summarize/vertaal 等，且代码分 <3；
   - `code`：代码块 +3、报错堆栈 +4、语言名 +2（每个，上限 2 个）、工具名（git/docker/nginx…）+1.5、文件名 +1、代码语法 +0.6、术语 +0.8、规模词 +1.5；分数 ≥3 且 ≥推理分×0.8 时判定；
   - `reason`：为什么/分析/权衡/证明/waarom/vergelijk 等每个 +1.2、数学词 +1.5、深度词 +1、列表 +0.8；≥2.4 判定；
   - 都不过线 → `chat`；代码分 ≥2 兜底判 `code`。
4. **难度 1–3**：代码规模词、推理深度、**本轮工具步数**、`reasoning_effort`；用户自己写的那段话很长（>1500 字）或上下文 >20 万 token 时各算一档。见 4.1。
5. **会话沿用**：匹配"继续/好的/ga door"等追问词，或 ≤4 字且无任何信号时，沿用同会话上一轮的任务（避免"继续"被当闲聊、换到弱模型并丢缓存）。
6. **纠正识别**：同会话 15 分钟内，用户说"不对/还是报错/that's wrong/klopt niet"等 → 沿用上一轮任务、**难度 +1**、上一轮那个模型的价值打五折、给上一条请求补 `user_correction` 标记并扣分。

**性能**：只分析最后一条用户消息的开头 2000 字 + 结尾 4000 字；文本先整体转小写再用 ASCII 模式匹配英文词（`re.I` 在长文本上明显更慢）。实测：短对话 0.01ms，1.5K 字代码题 0.9ms，20 万 token 长文 2.3ms（优化前 28ms）。

### 4.1 难度衡量的是"要多聪明"，不是"请求有多大"（2026-10-06 修正）

上线后用户反馈"随便一个小任务都在疯狂调 kimi k2.7"。实测复现，同一句"跑一下测试"：

| 请求 | 判定 | 够用线 | 每分价值 | 选中 |
|---|---|---|---|---|
| 3 个工具、无上下文 | `agent/1` | 7.4 | $0.0020 | deepseek-flash |
| 16 个工具、无上下文 | `agent/2` | 8.0 | $0.0060 | deepseek-flash |
| 3 个工具、58K 上下文 | `agent/2` | 8.0 | $0.0060 | deepseek-flash |
| **16 个工具、58K 上下文**（真实流量形态） | **`agent/3`** | **8.7** | **$0.0150** | **kimi-k2.7-code** |

任务一模一样，只是请求变大了。两个加档条件在编码 agent 上**恒为真**：

- `n_tools >= 12` —— 声明了多少工具是**客户端配置**，Hermes 每次请求都带 15–20 个，对"这次难不难"零信息量；
- `est_tokens > 50_000` —— 审计实测输入 p50 是 58K、均值 65.7K，长上下文是这个客户端的**常态而非信号**。

而难度 1→3 的每分价值跳 7.5 倍、够用线从 7.4 抬到 8.7。8.7 这条线上只有 kimi(8.7) 和 glm-5.3(8.6) 能过，deepseek-flash(7.3) 要吃 2.1 分的不足惩罚。再叠上订阅窗口空闲时影子价格在 5% 地板（kimi 标价 $0.076 的有效成本只有 $0.0038，是质量价值 $0.13 的 3%），成本项根本没有发言权 —— 系统事实上退化成纯质量最大化。

**根因不在成本模型，在分类器**：请求大小已经按 token 实打实计价了，再让它抬难度等于对同一件事收两次费。改为：

- 工具步数用**本轮**的（最后一条用户消息之后有几条 tool 回复）：≥5 加一档、≥15 再加一档。绕了十几步还没搞定，是真的不好办；
- 上下文长度只保留一档，阈值放到 >20 万 token；
- `code` 不再因为"贴了 150 行以上"加档（只说明贴得多），保留"≥2 个代码块"（多处改动）。

效果（58K 上下文、16 工具、一回合 8.6 次调用）：

| | 选中 | 一回合标价 | 预计等待 | 5 小时窗口 |
|---|---|---|---|---|
| 改前 | kimi-k2.7-code | $0.540 | 230s | 22 回合 |
| 改后 | deepseek-flash@opencode_go | $0.080 | 61s | **151 回合** |

升档路径仍然通畅且有证据支撑：绕了 16 步 → `agent/3` → kimi；"重构整个项目" + 绕了 6 步 → `agent/3` → kimi。质量不够的情况由**实测**兜底而不是先验猜测：验证器把工具参数非法记进 `OutcomeBook`，坏比率一上去路由自动换人（实测 flash 坏 40% 时自动移到 glm-5.3-flash），单次失败还有 Weitzman 定向重试。回归测试：`test_difficulty_ignores_request_size`、`test_difficulty_follows_loop_depth_and_scope`。

## 5. 路由打分（统一公式，单位美元）

```
score = 质量价值 − 有效成本 − 等待成本 − 风险成本

质量价值 = 有效质量分 × 该任务该难度「每分质量值多少钱」
          有效质量分 = min(q, 够用线) + 0.35×max(0, q−够用线) − 1.5×max(0, 够用线−q)
有效成本 = 按量：实付美元（含峰时倍率、会话缓存命中）
          订阅：标价美元 × 影子价格倍率
等待成本 = (首 token 预估 + 输出量/速度) × 该任务「每秒值多少钱」  ← 死线之内的次要偏好
死线     预计总耗时 > 该任务 deadline_s 的候选先排除（thalamus/fast 再除以 3）
风险成本 = 上游错误率 × 质量价值                      ← 传输失败：换家重试
         + 验证器坏比率 × (价值 + 成本 + 等待)        ← 内容不合格：整轮白做要重来
         （重新生成时该模型额外 +$1，纠正时价值打五折）
```

其中 `q = 配置里的质量先验 + 隐式反馈修正（限幅 −1.5 ~ +0.3）`。

**硬过滤**（不参与打分，直接排除并记录原因）：已停用、未配置 key、**原生上下文不达标**、本次已尝试、非指定模型、key 不允许此模型、**key 不允许此区域**、需要 pro 套餐、不支持图片、不支持工具、上下文不足（`room` 不够输出）、熔断中、渠道并发已满、按量日预算已用完、订阅额度不足或已耗尽、经济档单次上限。

其中"原生上下文不达标"属于配置层排除（和"未配置 key"同类），不会被当成客户端输入太长 —— 点名一个被门槛排除的模型返回 404 `model_not_available`，而不是 400 `context_length_exceeded`。

**延迟为什么要当约束而不是只当价格**：等待的效用不是线性的（300ms 和 500ms 用户无感，1s 和 3s 天壤之别），而线性加权（scalarization）还有个已知局限 —— 它只能取到 Pareto 前沿**凸包上**的点，带阈值性质的目标容易落在取不到的凹陷区。所以先用死线把不可接受的候选剔掉，剩下的再按价值比较；`usd_per_sec` 退化成死线之内的次要偏好。死线是"有牙齿的偏好"不是正确性要求：**所有候选都超线时把它们放回来按常规打分**，不把请求判死。

这样设计的好处：所有取舍在同一单位下比较，调参只改 `policy.yaml`；"便宜"和"聪明"自动平衡（闲聊每分质量只值 $0.0002，自然选便宜的；难 agent 任务值 $0.015，自然愿意上强模型）；**完全可解释**——管理台"路由试算"列出每个候选的每一项数值和被排除原因。

### 5.0 是质量在决定，还是成本在决定？（实测，2026-09-28）

把每个场景里"候选之间质量价值的极差"与"成本的极差"量出来比，谁大谁主导：

| 场景 | 质量极差 | 成本极差 | 主导项 | 选中 |
|---|---|---|---|---|
| chat/1 短闲聊 | $0.00006 | $0.00079 | 成本 | deepseek-v4.1-flash（7.6） |
| utility/1 翻译 | $0.00001 | $0.00031 | 成本 | deepseek-v4.1-flash（8.0） |
| code/1 普通代码 | $0.00480 | $0.00157 | **质量** | kimi-k2.7-code（8.8） |
| code/2 难代码 | $0.02312 | $0.00393 | 质量 | kimi-k2.7-code（8.8） |
| agent/1 工具循环 | $0.00798 | $0.00102 | **质量** | kimi-k2.7-code（8.7） |
| reason/3 深度推理 | $0.08070 | $0.01175 | 质量 | deepseek-v4-pro（8.9） |

**这张表是调完参数之后的**。调之前 code/1 与 agent/1 是成本主导：`code/1` 的 need 原本是 7.0，而 deepseek-flash 的 code 分 7.3 已经超线，8.8 分模型的超出部分只按 35% 计价，于是两者质量价值只差 $0.00053，被 $0.00157 的成本差压过 —— 为省 1.6 个 credit 的千分之一，放弃 1.5 分的代码质量。对一个服务编码 agent 的产品这是错的取舍，因为**答不好一次带来的重试/纠正，成本远高于那点差价**。

改法是把 code/agent 的够用线定在"能一次做对"而不是"大致能答"，并同步提高每分质量的计价：

```
code:  need 7.0→7.8 / 8.0→8.4 / 8.7→8.8    usd_per_point 0.001→0.003 / 0.005→0.008 / 0.015→0.02
agent: need 7.2→8.0 / 8.0→8.4 / 8.7→8.8    usd_per_point 0.002→0.004 / 0.006→0.010 / 0.015→0.02
```

验证过两点：订阅窗口空闲时与用到 70% 时，code/agent 都保持质量主导（不会窗口一紧张就掉回便宜模型）；chat/utility 不受影响，仍然是成本主导 —— 那里便宜是对的。

**两个必须写明的副作用**：

1. **更依赖 quality 先验**。提高 `usd_per_point` 等于放大质量项的权重，而那 9×7 个分数是我猜的、从未校准。也就是说这个改动让路由更"看质量"，同时让它对**错的质量分**更敏感。`scripts/calibrate.py` 的优先级因此更高了。
2. **订阅额度消耗变快**。code 类请求从 deepseek-flash 换到 kimi-k2.7-code，单次占 Go 五小时窗口约 0.26%（约 380 次/窗口），对个人 agent 量级够用；窗口填满后影子价格会自动把它推回便宜模型。

### 5.0.1 答错的代价（本地验证器，已实现）

原来公式里唯一没计价的就是这一项。现在有了：

**验证器**（`thalamus/verify.py`，不调用任何模型、只做结构检查、只留标记不留内容）：

| 标记 | 检查 | 学习权重 |
|---|---|---|
| `tool_args_invalid` | 工具参数不是合法 JSON | 1.0 |
| `tool_schema_invalid` | 参数是合法 JSON 但违反客户端声明的 schema：函数名不存在 / 缺必填 / 类型不符 / enum 越界 / `additionalProperties: false` 下有多余字段 | 0.9 |
| `json_invalid` | 要求 JSON 输出但返回的不是 | 0.6 |
| `code_invalid` | 明确标了语言的代码块解析不过（python / json / yaml） | 0.4 |

**设计取向是宁可漏报不可误报** —— 误报会污染学习信号，那比漏掉几个真错误糟糕得多。所以这些形态一律跳过：带 `...`/`省略` 的片段、REPL 回显（`>>>`）、shell 提示符、diff、没标语言的块、单行块；Python 报错里出现 `was never closed` / `unexpected EOF` / `unterminated` 的一律当成"输出被截断"而不是"模型写错了"。判不了的也一律放过：客户端没声明 tools、schema 用了 `anyOf`/`$ref`、没写 `additionalProperties: false` 时的多余字段。JSON 不区分 int 与 float，所以 `3.0` 是合法 integer、`3.5` 不是。代码检查只对 `code`/`agent` 任务开（别处的代码块多是片段，且顺带限制了缓存输出文本的内存）。

**定价**（`health.OutcomeBook`）：每（模型,任务）维护带时间衰减的计数，用 Beta 先验收缩成一个"坏比率"：

```
rate = (坏次数 + 0.03×20) / (总次数 + 20)        衰减 γ=0.995/次，半衰期约 140 次
risk_cost += rate × (质量价值 + 成本 + 等待成本)
```

先验收缩的意义：**样本少时贴近 3% 的先验，对所有候选一视同仁，不会因为一次失败就把某个模型判死**；持续失败才会被定价。衰减保证几周前的旧表现不会一直压着它。重启时用库里 14 天的 `outcome_stats` 做冷启动。

乘的是 `价值 + 成本 + 等待` 而不只是价值 —— 因为一次坏回答意味着**整轮白做且要重来**：用户没拿到价值，网关要再付一次成本、用户要再等一次。这正是"用好模型省下的重试"在公式里出现的方式，不需要手调 `need` 线。

实测（`test_verify.py`）：让胜出模型在某任务上连续失败 300 次，它的 `risk_cost` 涨到基线的 5 倍以上，排序让位给别的模型；坏比率与样本数在管理台"学习与配置"页可见。

### 5.0.2 验证失败后的定向重试（Weitzman 保留值规则，已实现）

有了可观测的信号，"要不要换个模型重做"就变成一个最优停止问题。Weitzman(1979) 的潘多拉盒子给了闭式解。把奖励建模成伯努利（`1−p` 概率拿到 `value`，`p` 概率拿到 0），代入 `E[max(X−σ,0)] = c`：

```
σ = value − (成本 + 等待成本) / (1 − p)          p = 验证器坏比率
换谁 = argmax σ，门槛 = 失败候选自己的 σ（后验 p 取 max(实测, 0.5)）
```

**门槛取失败候选的 σ 而不是 0** —— 这一点是实测逼出来的：任务价值表只为*相对排序*校准过，绝对值没有意义（chat/1 的 score 本来就是负的），拿 0 当门槛会让所有便宜任务永不重试。换成相对比较后规则是尺度无关的，同时仍然是保留值规则。

**什么时候才缓冲**（这是能不能重试的前提）：

| 情形 | 行为 |
|---|---|
| 非流式 | 总是验证后再返回（本来就要收齐，缓冲零代价） |
| 流式 + 有 `tools` 或 `response_format` | 缓冲后验证（客户端拿不到半个工具调用或半个 JSON，缓冲不影响体验） |
| 流式散文 | **不缓冲、不重试** —— 一旦开始流就不能收回 |
| 缓冲超过 `buffer_kb`（默认 64KB） | 放弃重试，恢复真正的流式 |

**重试整体放在响应开始之前**（`Call.resolve()`，在 `engine.open()` 里 `connect()` 之后）。必须如此：HTTP 响应头先于 body 发出，等流到一半才换模型会让 `X-Thalamus-Model` / `X-Thalamus-Attempts` 说谎。

**账怎么算**：被丢弃的那次由网关承担（与对冲落败同一处理，记入实付与订阅窗口、不计入用户额度），用户只为重做的那次付费。第一次的负面信号照样记在那个模型头上 —— 否则学习闭环就断了。请求日志打 `verify_retry` 标记。

**两个实现期踩到的坑**（都已修并有测试覆盖）：

- 缓冲过的片段回放时被**重复计量**，工具参数被拼成两遍，结果把一个合法调用判成了非法 JSON。现在回放走单独通道，不再计一次量。
- 重试连不上时必须把第一次的结果原样交出去，而不是让整个请求失败。

实测：第一次给出违反 schema 的参数 → 换模型重做 → 客户端拿到的是合法调用，`attempts=2`，日志里 `tool_schema_invalid,verify_retry`，失败模型的坏比率与质量分都被扣了。

**这一项解锁了什么**：剩下的就是 Bandits-with-Knapsacks 式的在线学习（见第 15 节）—— 验证器提供奖励，`OutcomeBook` 提供后验，保留值规则提供探索顺序，三块都在了。

### 5.1 订阅额度的影子价格（便宜量大的核心）

价格 = **学到的水平 λ × 理论形状**，并按本次消耗的区间取平均：

```
形状   p(u) = exp(κ(u − full))，κ = ln(1/floor) / (full − knee)
增量   本次消耗 u₀→u₁ 的倍率 = (1/Δu)·∫p(u)du = [p(u₁) − p(u₀)] / (κ·Δu)
下限   不低于 floor；u₁ ≥ safety 直接排除
水平   λ ← clip(λ · exp(η · tanh(观测速率/窗口可持续速率 − 1)), lam_min, lam_max)
```

**为什么是指数形状**：在线预算分配的最优折价函数是指数型 —— AdWords 问题（Mehta–Saberi–Vazirani–Vazirani）在对抗到达下的最优竞争比 1 − 1/e 就是由 `1 − e^{x−1}` 这类函数达到的，分段二次是手画的。κ 由原来的 `floor/knee/full` 反解，所以**配置口径不变**：`u = knee` 时正好是 floor，`u = full` 时正好是 1.0。实测两条曲线在锚点重合，中段新曲线略平缓（75%：0.425 vs 0.535），末段也略平缓（95%：2.35 vs 3.78）。

**为什么取区间平均**：一次消耗 Δu 的真实增量成本是 `C(u₁) − C(u₀)`，不是 `p(u₁)·Δu`。旧写法按终点的边际价乘以全部用量，对大请求是**高估**。实测（λ=1）：

| 消耗区间 | 区间平均 | 终点边际价 |
|---|---|---|
| 84%→85% | 0.958 | 1.000 |
| 60%→85% | 0.412 | 1.000 |
| 0%→85% | 0.137 | 1.000 |

**这个修正的代价要说清楚**：它让"窗口中段的大请求"比原来便宜约 2.4 倍，也就是**削弱了末段的刹车**。刹车现在由三样东西提供：`safety`（硬排除）、`single_share`（产品取舍）、以及学到的 λ。如果上线后看到窗口被填得过快，调的是 `single_share` 往下或 `eta` 往上。

**为什么 λ 要学**：`knee`/`full` 决定形状，但真正的价格水平取决于"你的流量相对预算有多大"，这个没法猜。对偶镜像下降（Balseiro–Lu–Mirrokni 的 online allocation 方案，指数化梯度形式）用观测消耗速率对窗口可持续速率的偏差做梯度步，在随机到达与对抗到达两种情形下都有最优 regret。`tanh` 限幅是为了一个超大请求不会把价格一步打到上限。实测（glm_plan 的 5 小时窗口，上限 2000 积分、可持续 0.111 积分/秒）：

| 流量 | λ | 50% 利用率时的价格 |
|---|---|---|
| 以 20 倍可持续速率猛用 | 3.49 | 0.174（λ=1 时 0.050） |
| 回到 1 倍速率 | 3.47 | 0.174（恰好在目标速率上不动，符合设计） |
| 几乎不用 | 1.17 | 0.059 |

关掉自适应（`adaptive: false`）就退回 λ≡1，也就是纯配置曲线。

**单次占比项**（保留）：理论在低利用率区把闲置额度定价为≈0，这在"用了不花钱、不用就作废"的前提下是对的；但"一次请求不该以地板价买走整个窗口"是个产品取舍，而 λ 只在事后才涨得起来。所以单次占比超过 `single_share`（默认 0.15）时按 `(占比/阈值)²` 抬价，与上面取大者。

窗口计数按分钟分桶、持久化在 SQLite，重启不清零；上游返回额度耗尽时标记该渠道冷却（默认 30 分钟）后自动恢复。

### 5.2 会话缓存粘性是算出来的

DeepSeek 缓存命中价是未命中的 1/50，多轮对话里缓存通常占输入大头。网关记住每个会话上次用的候选与提示词长度（只存哈希），同一候选按缓存价估算、换家按全价估算。于是会话默认留在原处（因为便宜），但当别家的质量或速度优势超过丢缓存的代价时照样会换。客户端不带会话 ID 时，用 `key + system 开头 + 第一条用户消息` 的哈希自动识别会话。

### 5.3 隐式反馈（有界、可审计）

延迟与速度：每候选首 token 与输出速度滑动平均，直接进等待成本。
错误率：滑动平均进风险成本；连续失败触发熔断（指数退避，半开只放一个探测）。
质量修正：只来自客观信号，单次幅度 = `learning.penalty × 权重`，总幅度限幅：

| 信号 | 含义 | 权重 |
|---|---|---|
| `tool_args_invalid` | 工具调用参数不是合法 JSON | 1.0（同时计入 agent 任务） |
| `user_correction` | 下一轮用户在纠正这次回答 | 0.7 |
| `json_invalid` | 要求 JSON 输出却不合法 | 0.6 |
| `empty` | 正常结束却没有正文 | 0.6 |
| `regenerated` | 下一轮用户重新生成同一问题 | 1.0 |
| `truncated` / `quota_cut` / `hedged` | 只记录，不参与学习 | — |

正常完成（无负面信号）缓慢回升。全部在管理台"学习与配置"页可见，也在 `/metrics` 导出。

**刻意没做**：让 LLM 自动改路由配置、bandit 探索流量。请求量不大时噪声大于收益。

## 6. 配额与计费

- **1 credit = $0.001 标价用量**。订阅渠道也按标价折算，用户额度与内部走哪家无关——对用户公平可预测，也不泄露渠道信息。
- **每日重置**，时区可配（默认 `Europe/Amsterdam`）。
- **预留 → 结算两段式**，账本在内存：asyncio 单线程，检查与扣减之间没有 await，天然原子。有测试：20 个并发、额度够 15 个，恰好通过 15 个。
- **超额策略**（按 key）：
  - ≥80%：成本权重 ×3，更倾向便宜模型；
  - ≥100%：`economy` 只允许单次 ≤3 credits 的经济档，另有 15% 宽限带；`reject` 直接 429（带 `Retry-After` = 距重置秒数）；
  - `daily_credits = 0` 表示**冻结**（不是不限）；RPM 与并发最小为 1，没有"不限"选项。
- **单次请求硬预算**：防止用超大 `max_tokens` 或并发把日额度打穿，超出即截断（`finish_reason=length`，日志标记 `quota_cut`）。另有默认单次输出上限 32768 token。
- **全局按量日预算**（默认 $20）：接近上限时按量候选成本权重上升，达到上限后按量候选全部排除，只剩订阅可用。
- **对冲落败方的成本**由网关承担，记入实付/订阅用量，不计入用户额度。

## 7. 性能（实测，Windows 11 / Python 3.12 / 16 逻辑核）

`scripts/loadtest.py`：网关、模拟上游、压测客户端三个独立进程，分别统计 CPU。测试条件：上游首 token 300ms，每请求 40 片 × 5ms；混合流量含 10% 的 3 万 token agent 请求。

| 并发 | 网关附加首 token p50 / p99 | 吞吐 | 网关 CPU | 内部路由开销 |
|---|---|---|---|---|
| 1 | 11 / 9 ms* | 3 RPS | 4% | p50 ≤1ms，p99 ≤2.5ms |
| 10 | 0.8 / 11.5 ms | 28 RPS | 28% | 同上 |
| 20 | 16.7 / 36.8 ms | 49 RPS | 50% | 同上 |
| 40 | 客户端 CPU >80%，数字不可信 | ≈60 RPS | ≈63% | — |

\* 上游首 token 设为 0 时，并发 1 的附加开销是 4.8ms；300ms 条件下的 11ms 大部分来自 Windows 约 15.6ms 的定时器精度。

- **冷启动**：不预热连接时首个请求多 550ms；预热后只比直连多约 30ms。因此启动时预热，并每 45 秒保温（连接池 keepalive 120 秒）。
- **优化历史**：
  - 请求准备阶段 20.3ms → **0.94ms**（内存账本 + 批量写库，原因是 SQLite 读写全部串行排队）；
  - 长文分类 28ms → **2.3ms**（窗口化 + 小写化 + ASCII 词边界；一开始我猜是正则回溯，实测不是）；
  - 缓存击穿：冷启动 50 并发各查一次库（平均 62ms）→ 单飞查一次。
- **写缓冲的代价**：进程异常退出最多丢最近 250ms 的日志与用量；正常关闭先刷盘。
- **退出必须保证能退出**（2026-10-12 修）：aiosqlite 的连接跑在**非守护线程**（`daemon=False`）上，不关掉的话解释器会在 `threading._shutdown` 里 join 它直到永远。所以 ① `startup()` 中途失败要先 `store.close()` 再抛（否则一个 `data/` 权限问题会表现成 `systemctl start` 卡住 90 秒后被 SIGKILL，真正的 traceback 根本看不到）；② `shutdown()` 的每一步都要走到，前一步抛异常不能连带让连接关不掉 —— 刷盘失败只丢 250ms，卡住退出丢的是整个缓冲。覆盖：`test_startup_failure_closes_the_db_instead_of_hanging_exit`、`test_shutdown_closes_the_db_even_if_an_earlier_step_raises`。
- **吞吐上限未实测到**：并发 40 时压测客户端先饱和。按 1 RPS ≈ 1% CPU 推算，单进程约 90–100 RPS。要确认需把客户端放到另一台机器并在 Linux 上测。

### 7.1 收到请求 → 发出上游请求（实测，分阶段）

口径：真实 ASGI 应用 + `httpx.MockTransport`，链路里除 TCP/TLS 外每一步都是真的（鉴权、读体、限流、意图、配额、打分、预留、适配器构造、连接池取用）。假上游在被调用的第一刻记时间戳，与客户端发出时刻相减。同一套客户端栈上 `GET /health` 的往返基线是 **p50 1.09ms**，所以短请求那 1.6ms 里大部分是 HTTP/ASGI 栈本身，不是网关的判断逻辑。

| 请求 | 端到端（发出→上游收到） | 读体+JSON | 特征+意图 | 配额+打分+预留 | └ 其中打分 | 鉴权 |
|---|---|---|---|---|---|---|
| 短对话（6 token） | **1.6 / 2.2ms** | 0.02ms | 0.04ms | 0.24ms | 0.15ms | 0.01ms |
| 代码问题（644 token，含 400 行代码块） | **3.3 / 4.1ms** | 0.03ms | 1.65ms | 1.86ms | 0.15ms | 0.01ms |
| 中等上下文（3 万 token） | **5.3 / 6.4ms** | 0.61ms | 2.80ms | 3.02ms | 0.15ms | 0.01ms |
| 满窗口（89 万 token，3.7MB） | **42.5 / 49.1ms** | 19.9ms | 10.5ms | 10.8ms | 0.21ms | 0.02ms |

（格式为 p50 / p95；阶段列为 p50。并发 1。）

三个结论：

1. **打分本身永远是 0.15–0.21ms**，与上下文大小无关 —— 候选数固定（9 个 offer），每个候选只做几十次算术。"聪明"不花时间。
2. **开销全在"碰文本"上**：读体+JSON 解析、token 估算、正则扫描。1M 请求的 42ms 里有 30ms 是这两件事，且都随字节数线性增长。
3. **鉴权几乎免费**（0.01ms）：key 按哈希在进程内缓存 10 秒，命中时不查库。

并发下单进程是串行的，固定开销会排队：

| 并发 | 短对话 | 中等上下文（3 万 token） |
|---|---|---|
| 1 | 1.6 / 2.2ms | 5.3 / 6.4ms |
| 10 | 10.2 / 15.4ms | 33.0 / 50.8ms |

10 个 3 万 token 的请求同时到达时，最后一个要等约 33ms 才被发往上游 —— 这是 Python 单进程的代价，也是"吞吐上限约 90–100 RPS"的来源。相对上游 0.9–1.8s 的首 token 仍然是小头，但如果要做高并发长上下文，这里就是第一个要拆的地方（多进程 + 共享状态移到 Redis，见第 15 节）。

**不包含**：到上游的网络 RTT 与 TLS 握手（连接池命中时约 30ms，冷启动曾达 550ms，已用启动预热 + 45 秒保温解决），以及上游自身的首 token 时间。**到 DeepSeek/GLM 的实际 RTT 未实测**，它在真实链路里远大于网关自身开销。

### 7.2 为什么是单进程，以及并行的路怎么走

**等上游的部分早就是并发的**（asyncio），几百条流同时在跑没问题；串行的只有每请求那 0.3–42ms 的 CPU。

**线程解决不了**（Python 3.12.10 实测，工作内容 = `json.loads` + 特征提取 + 意图判定）：

| 输入 | 串行 8 次 | 2 线程 | 4 线程 | 8 线程 |
|---|---|---|---|---|
| 3 万 token | 28.5ms | 0.96× | 0.90× | 0.97× |
| 89 万 token | 214.1ms | 1.05× | 0.99× | 1.03× |

`json` 的 C 扫描器、`re`、`str.encode` 全程持有 GIL，所以线程池加速比在 1.0 附近波动 —— 卸载到线程只会多一次上下文切换。要并行只能多进程。

**多进程会把这些进程内状态打碎**（这就是"多实例"不是加个 `--workers` 就完事的原因）：

| 状态 | 打碎的后果 |
|---|---|
| `Ledger` 每日额度 | 每个进程各放行一份上限 → 最多超发 N 倍 |
| `Limiter` RPM / 并发 | 同上，限速形同 N 倍 |
| `CapacityTracker` 订阅窗口 | **最危险**：各进程只看见自己那份用量，都以为窗口空着 → 冲破 5 小时上限、吃上游 429 |
| `_metered` 按量日花费 | 钱包上限也变成 N 倍 |
| `SessionMemory` | 前缀缓存粘性失效（1M 下这是 50 倍的杠杆）、"继续"被误判、重新生成检测失灵 |
| `HealthBook` 熔断 | 不算错，只是反应慢 N 倍、多浪费 N 倍失败请求 |
| 管理台 Cookie 会话 | 轮询转发时登录态只在签发它的那个进程有效，控制台直接不可用 |

**两条路，推荐第二条**：

1. **共享状态到 Redis**（路线图第 8 项）：正统做法，但要写原子的 reserve/settle（Lua）、滚动窗口、会话 KV，还要设计"Redis 挂了怎么降级"。工作量一到两天，并且引入这个项目目前没有的外部依赖。
2. **按 API key 分片**（更便宜，而且正好贴合这个设计）：前置代理按 `Authorization` 哈希到固定进程。额度、限速、会话记忆、key 缓存**全都是按 key 的状态**，分片后天然待在同一个进程里，不需要共享；会话 key 本身就是从 `key_id` 派生的（`features.py`），所以缓存粘性也自动保住。只剩三样要额外处理：订阅窗口与按量日上限（全局，可先粗暴地按进程数均分额度，或只为这两个计数器上一个共享后端）、管理台（把 `/admin` 固定到 0 号进程）。nginx 用 `hash $http_authorization consistent`；Caddy 的 `lb_policy` 也有按请求头哈希的策略，用前要核对文档。

**现在不做的理由**：短请求的 CPU 是 0.3ms，一个核能做约 3000 次/秒的路由；真正会先饱和的是流式分片处理（约 0.2ms/片，按之前压测反推），这也是"单进程约 90–100 RPS"的来源。而并发 10 的 33ms 排队相对上游 1–2 秒的首 token 只有 2–3%。等真的需要 >100 RPS 再上分片，比现在提前引入 Redis 划算。

### 7.3 "感觉没有 GPT 客户端快"该去哪儿找（2026-10-10）

先把网关自己摘出来。假上游立刻吐第一片（上游 ttft = 0），量客户端看到第一个字节的时刻：

| 客户端用法 | 网关附加首字 |
|---|---|
| 流式闲聊 | **2.5ms** |
| 非流式闲聊 | 2.3ms |
| 流式工具调用（走验证缓冲） | 2.4ms |
| 非流式、10 万字长回答 | 53.6ms（全部重新组装的代价） |

加上 7.1 的派发开销（短请求 1.6ms），**网关在首字上的贡献是个位数毫秒**。它不是感知差距的来源。真正的四段，按量级排：

| 来源 | 量级 | 谁能改 |
|---|---|---|
| **地理距离** | 荷兰 → 北京单程 RTT 80–120ms，冷连接还要 +2 个往返做 TLS | 只能复用连接（已做：启动预热、每 45s 保温、keepalive 120s）。距离本身改不了 —— OpenAI 客户端打的是 anycast 边缘节点，通常 <30ms |
| **反代攒包** | 看起来像"全程卡住然后一次性吐出来" | nginx 默认 `proxy_buffering on` 会毁掉 SSE，必须按 `deploy/nginx.conf` 关掉；Caddy 要 `flush_interval -1` |
| **客户端要了 `stream:false`** | 等待时间 = 整段生成时间 | 客户端设置。网关对上游一律用流式，但客户端要非流式就只能等它攒完 |
| **上游自己的首 token** | 1–5s，`kimi-k3` 先验就写着 5.0s | 路由能选，但前提是它知道谁快 —— 见下 |

`scripts/latency.py` 把这四段拆开量（在网关机器上跑一遍、在客户端机器上再跑一遍，差值就是中间那一段），并按分片到达的间隔自动判断有没有被攒包。

**其中一项确实是网关的 bug，已修**：`HealthBook` 只在内存里，启动时从不回灌。于是每次重启都把实测的首 token / 出字速度丢掉，退回 `upstreams.yaml` 里那份先验 —— 而那份先验 ① 是猜的（`glm-5.3` 写着 `tps: 50`，校准实测一次回答 8.5–36.7s）、② **跟模型走、不区分渠道**，因此在数学上不可能分辨"荷兰 → 北京"和"荷兰 → 美国"。等待成本和死线全读这两个数。

修法与 `OutcomeBook` 一致：启动时用 `store.latency_stats()` 回灌（3 天窗口、每组 ≥5 个成功样本）。按 `(model, channel)` 分组是关键，出字速度只从首 token 之后那段算，否则等待会被算进吞吐。实测效果 —— 同一个 `deepseek-v4.1-flash`，两个渠道：

| | 回灌前（= 先验） | 回灌后（= 实测） |
|---|---|---|
| @deepseek（北京） | 0.90s / 80 tps | **1.15s / 40 tps** |
| @opencode_go（美国） | 0.90s / 80 tps | **0.31s / 78 tps** |

回灌前两个渠道完全同分，路由只能靠价格区分；回灌后 400 token 的回答预计 11.2s vs 5.4s，等待成本自然把延迟敏感的任务推向近的那家。覆盖：`test_latency_seed_survives_restart_and_separates_channels`。

## 8. 上游适配器

- **`openai_chat`（DeepSeek、GLM Coding Plan、OpenCode Go 多数模型）**：近乎原样透传。只改 `model`、强制流式并要求返回 usage、按 key 与剩余窗口限制 `max_tokens`、丢掉 `n`（多份候选成倍消耗而只转发一份）。tools、tool_choice、图片、response_format 等一律不做有损转换。
- **`anthropic`（Go 上的 MiniMax 等 `/messages` 模型）**：双向翻译。system 字段、`tool` 角色 → `tool_result`、`assistant.tool_calls` → `tool_use`、`image_url`（data:/http）→ image、tools/tool_choice 转换、相邻同角色消息合并；响应端 `text_delta` → content、`thinking_delta` → reasoning、`tool_use` + `input_json_delta` → OpenAI 工具调用增量（保持 index/id/name）。
- **usage 归一化**：DeepSeek 的 `prompt_cache_hit/miss_tokens`、OpenAI/智谱的 `prompt_tokens_details.cached_tokens`、Anthropic 的 `cache_read/creation_input_tokens` 统一成 `input_miss / input_cached / output / reasoning`。
- **`<think>` 拆分**：正文里夹的 `<think>…</think>` 挪到 `reasoning_content`，跨分片安全。
- **`max_tokens` 规则**：客户端值 → key 上限截断 → reasoning 模型抬到 `min_max_tokens`（预算太小会没有正文）→ 模型 `max_output` 封顶。
- **错误分类**：401/403→鉴权（带额度字样则算额度耗尽）、402→额度、429→按文案分速率或额度、400/413/422→上下文超长 / **模型契约不匹配（见 8.1，可换模型重试）** / 客户端错误、404/405→当作渠道故障（模型名不对时可换家并熔断）、5xx→渠道故障。

### 8.1 模型专属的请求契约（`MODEL_INCOMPATIBLE`，2026-10-12）

线上故障：webui 从第二轮对话起反复

```
HTTP 400 The `reasoning_content` in the thinking mode must be passed back to the API.
```

**不是网关造成的，但网关本来有能力消化掉它，却选择了把 400 转给客户端。** 和 kimi-k2.7-code 的 `temperature` 是同一类 bug：某个模型有自己的请求契约，网关"近乎原样透传"的策略把它直接暴露给了客户端。

成因链：

1. 请求路由到 `reasoning: always` 的模型（`glm-5.3` / `glm-5.3-flash` / `kimi-k3`），它返回 `reasoning_content`，网关如实转发给客户端（`engine.py` 流式与非流式两条路都带）。
2. 下一轮客户端把历史发回来。**`reasoning_content` 不是 OpenAI 规范里的字段**，绝大多数 webui 不存、更不回传。
3. 又路由到思考模型 → 它要求回传 → 400。
4. `classify_http(400, ...)` 判为 `CLIENT_ERROR` → `RETRYABLE` 不含它 → 直接抛给客户端。

于是只要客户端不回传，多轮对话就**必然**在第二轮失败，而且是间歇性的 —— 取决于这一轮有没有被路由到思考模型。

两道修复，分工明确：

**① 路由时排掉（主）**。这是能力不匹配，和"不支持图片""不支持工具调用"同一类硬约束，不是偏好：

```python
if f.reasoning_echo is False and m.needs_reasoning_echo:
    return "思考模型要求回传 reasoning_content，客户端没有回传"
```

`Features.reasoning_echo` 三态：`None` = 历史里还没有 assistant 轮次（第一轮，不会出问题）、`True` = 最后一条 assistant 消息带着它、`False` = 不带。只看最近一条 —— 客户端要么整体回传要么整体不回传，而上游检查的是最近那轮。`ModelSpec.needs_reasoning_echo` 默认跟 `reasoning: always` 走，可在 `upstreams.yaml` 里逐个覆盖。

排掉是**正确的**而不是保守的：如果客户端不能回传 `reasoning_content`，那么这个模型在思考模式下就是真的服务不了这个客户端的多轮对话。拒绝理由在管理台路由试算里可见，可审计。

**② 400 不再是死路（兜底）**。新增 `FailureClass.MODEL_INCOMPATIBLE`：请求本身没问题，是这个模型吃不下它 —— 换一个就能成。它是 `RETRYABLE` 的，并且

- 失败时把**整个模型**（不只是这个 offer）加进 `bad_models`：同一个模型在别的渠道上还是同一个模型，不该再白试一遍；
- 不计入错误率、不触发熔断（和 `CLIENT_ERROR` / `CONTEXT_OVERFLOW` 一样早返回）—— 能力不匹配不是上游有毛病，算进去会污染路由的风险成本，连续三次还会把一个健康的模型熔断掉。

命中特征串包括 `reasoning_content`、`must be passed back`、`thinking mode`、`only 1 is allowed for this model`（kimi 那条）、`does not support` / `unsupported parameter` 一类。

**没有做的一种修法**：网关其实见过那段 `reasoning_content`（是它转发出去的），理论上可以按会话存下来、下一轮替客户端补回去。不做，因为与"网关不存储任何原文、只存指纹哈希与计量元数据"这条硬约束冲突。排掉模型的代价只是换一个候选，存原文的代价是整个隐私口径。

覆盖：`test_thinking_models_excluded_when_client_drops_reasoning_content`、`test_model_incompatible_400_switches_model_instead_of_failing`。

## 9. 安全与防白嫖（`tests/test_security.py` 覆盖）

- **没有有效 key 碰不到上游**：唯一调用上游的入口是 `/v1/chat/completions`，读请求体之前先鉴权；没有"本机免 key"模式；管理口令不能当 API key 用。测试枚举所有路由 × 11 种伪造凭据 × 大小写/斜杠/路径穿越变体，断言假上游收到 0 次调用。
- **吊销立即生效**：停用、过期、轮换、删除、冻结（额度 0）都验证过。
- **单次请求不能打穿日额度**：硬预算 + 实时截断 + 默认输出上限。
- **发完就断也计费**：请求已送达上游、首 token 前断开，按输入估算计费。
- **0 不等于不限**：额度 0 = 冻结；RPM/并发 ≥1。
- **会话 ID 一律哈希并绑定 key**：不会原样进上游请求头（否则可被构造成上游报错、触发熔断影响所有人）。
- **请求体上限 32MB**（为 1M 上下文留出余量）、**无效 key 负缓存 + 同 IP 失败限流**（防止随机 token 刷库）。
- **区域白名单是硬约束**：限定区域的 key 在换家、对冲、降档、点名模型任何路径上都不会越界，两个同区渠道全挂时宁可失败也不跨区兜底（见 1.1）。
- **上下文门槛是硬约束**：被 `min_context_tokens` 排除的模型点名也用不到，`/v1/models` 里也看不到（见 1.2）。
- **管理台**：HttpOnly + SameSite=Strict Cookie，登录失败限流（10 分钟 8 次），建议再加 Caddy 的 IP 白名单；`/metrics` 需要 Bearer token。
- **上游密钥不进数据库、不进备份、不回显**：控制台设的 key 存 `data/secrets.json`（0600），管理接口只返回 `sk-a…b12c` 形式的掩码；每日备份是 `VACUUM INTO`，只含 `.db`。
- **控制台加渠道的输入全部校验**：渠道 id 限 `^[a-z][a-z0-9_-]{1,31}$`（挡路径穿越，文件名由它拼），Base URL 必须 http(s)，价格/上下文/并发都有上下界，模型名限字符集；配置写盘后若加载失败会**删文件回滚**再报错，不会留下坏配置。
- **来源 IP 只认可信代理给的值**：按 IP 的两处限流（鉴权失败、管理台登录）都用 `request.client.host`，也就是 uvicorn 按 `THALAMUS_TRUSTED_PROXIES`（默认只信 127.0.0.1）校验后的值。自己解析 `X-Forwarded-For` 会被伪造最左项绕过 —— Caddy 只在链尾追加真实 IP。若换成不做 proxy-headers 的服务器，这两处限流会退化成全局限流（更严，不会被绕过）。

**仍存在的风险**：持有有效 key 的人可以故意发让上游报错的请求来触发熔断影响其他用户（有冷却、会自动恢复，日志可追到是哪个 key）；也可以反复"重新生成"小幅压低某个模型的分数（有限幅）。

## 10. 隐私与合规

- 数据库与日志**不存任何提示词或回复内容**，只有计量与路由元数据；会话标识是哈希。
- 响应头给出实际模型（`X-Thalamus-Model`）满足 AI Act 第 50 条的透明度，但**不暴露渠道**（信息差）。
- key 只存 SHA-256，完整 key 仅在创建与轮换时显示一次。
- 每日自动备份到 `data/backups/`，保留 7 份。
- 跨境传输：GDPR 不禁止，需要合法依据 + 传输机制（SCC + 传输影响评估）并如实披露处理者类别。**中国方向的评估更难站得住**，B2B 客户可能直接拒绝——这正是 EU-only 溢价档的价值。（不是法律意见，对外前需荷兰本地顾问复核。）

### 12.1 在控制台自助加渠道（不用改文件、不用重启）

渠道页 → **＋ 添加渠道**，三步：

1. **填基本信息**：渠道 id、区域、Base URL（到 `/chat/completions` 之前那一段）、API key、协议（OpenAI 兼容 / Anthropic）、并发上限。
2. **点"探测可用模型"** → 网关用这把 key 调上游 `GET /models`，返回模型列表；能认出来的上下文长度（`context_length` / `context_window` / `max_model_len` / `max_input_tokens` 等字段）会自动预填，认不出来留空让人填。探测不写任何配置。
3. **勾选模型并填价格** → 保存。每个模型要填输入价 / 缓存价 / 输出价（USD per 1M token）、上下文、单次输出上限、质量先验（0–10）、是否支持工具与图片、思考模式。保存后立即热生效，**不需要重启**。

落盘方式：

| 内容 | 位置 | 为什么 |
|---|---|---|
| 渠道与模型定义 | `config/channels.d/<id>.yaml`，一个渠道一个文件 | 不去改 `upstreams.yaml`（会冲掉里面的注释）；仍是可手写、可进版本库的 YAML |
| API key | `data/secrets.json`（0600） | 不需要改 `.env` 重启。备份走 `VACUUM INTO`，只含 `.db`，所以密钥不进每日备份 |

key 的解析顺序是 **运行时密钥 → 环境变量**，所以：

- 控制台给任意渠道换 key 都立即生效，包括 `upstreams.yaml` 里那三家（运行时值覆盖环境变量）；
- 没在控制台设过的渠道，行为与以前完全一样。

`channels.d/` 里的渠道（列表里标"控制台添加的渠道"）可以在页面上停用/启用/删除；`upstreams.yaml` 里的渠道只允许换 key，停用与删除要改文件后点"重载配置"—— 避免控制台把手写配置改得对不上。

**每个模型旁边的"测试"按钮**向上游真发一条最小请求，回显：上游模型名、首 token、`finish_reason`、**解析出来的 usage 字段**、有没有思考内容、以及失败时**网关把这条错误判成了哪一类**（`rate_limited` / `quota_exhausted` / …）。最后这一项是上线前最该逐条核对的东西 —— 熔断策略靠它，判错了要改 `adapters/base.py` 里的关键字表。这条测试请求会产生真实费用，但不计入任何用户额度，也不写请求日志。

限制与取舍：

- **只支持按量渠道**。订阅渠道要填积分系数、窗口上限、折算方式，表单表达不了，仍然手写 YAML。
- **价格必填**，不给默认值。按量渠道价格填 0 会让它在打分里变成"免费"，从而吃掉所有流量。
- **质量先验默认 7.0**（七类任务同值），只是能跑起来的占位值，之后用 `scripts/calibrate.py` 校准。
- 模型 key 与已有模型同名时**复用已有的能力与质量定义**，只是多挂一个渠道（比如同一个 DeepSeek 模型同时走直连和 Go）。
- 新渠道同样受 1M 上下文门槛与区域白名单约束：加进来但不达标的模型会在启动校验里被列出来，路由不会用它。

### 上线前必改
1. `glm_plan.budget.windows`：按实际套餐档位填积分上限（Lite 2000/10000、Pro 12000/60000、Max 28000/140000）。
2. `opencode_go.budget.scope`：确认 Go 的额度是所有模型共用（`shared`）还是按模型分开（`per_model`）。
3. 各 `upstream` 模型名：以 `python scripts/probe.py --models` 或控制台渠道页的**探测/测试按钮**为准（尤其 DeepSeek 的 `deepseek-flash` 这个 ID 我只从定价页读到，**未实际调用验证**）。
4. `global.daily_metered_usd_cap`：按量渠道每日花费上限。
5. `models.<key>.context`：DeepSeek/GLM/Kimi 均按 1M 记（用户确认），**但未用 `probe.py` 实测**。它直接决定 `min_context_tokens: 1000000` 排掉谁（见 1.2），必须核对；顺带确认 MiniMax M3 是否也是 1M。
6. `keys.daily_credits: 2000`：1M 产品下的占位值（一次 90 万 token 请求约 136 credits，峰时 272），按实际定价重新算。
7. `subscription_pacing.single_share: 0.15`：允许单次请求占掉订阅窗口的比例。填小了长上下文永远走按量（贵），填大了一次请求就能买走整个窗口。
8. `.env`：三个上游 key + `THALAMUS_ADMIN_TOKEN`（可选 `THALAMUS_METRICS_TOKEN`、`THALAMUS_KEEPWARM_S`、`THALAMUS_TRUSTED_PROXIES`）。

```bash
python scripts/calibrate.py --via https://api.example.com --key sk-thl-xxx --judge deepseek-v4-pro
```

经网关模式的好处：不用把上游 key 复制到第二台机器；模型名从 `/v1/models` 取；花费受那把 key 的每日额度兜住；而且走的是真实数据面，顺带验证了"点名这个模型确实能用"（响应头的 `X-Thalamus-Model` 与点名不一致时会在报告里标出来）。

两条防止"把配置改坏"的规则：

- **裁判输出解析不了 ≠ 模型答得差**。前者这道题作废，后者按 0 分计。混在一起的话，一个不合适的裁判会把所有模型的先验一起拉低 —— 这是用假上游演练时真实发生过的（建议值把 7.5 打到 3.8）。
- **样本 < 2 的（模型,任务）保持先验不变**，报告里会列出来。12 道题每类只有 1–2 道，单个样本就改先验太激进。

**仍未用真实 key 跑过**，所以 `upstreams.yaml` 里那些 quality 数字到现在还是猜的。

**压测**：`python scripts/loadtest.py --levels 1,10,20 --warm`，见第 7 节。

**CI**：`.github/workflows/tests.yml` —— 测试 → 路由评测门槛 → 短时冒烟压测（有错误则失败）。

## 14. 代码审核结论

审了最近改动最大的部分（内存账本、批量写库、对冲、结算路径、鉴权）。**已修复**两项：请求体无上限、无效 key 无限流（均已补测试）。此后又补了区域白名单（1.1）与 1M 上下文门槛（1.2），相关取舍写在各自小节里。

剩余问题按优先级：

| 优先级 | 问题 | 位置 | 说明 |
|---|---|---|---|
| 中 | 适配器自身的异常会被当作可重试的上游故障 | `engine.py` `_try` 的 `except Exception` | 我们自己代码的 bug（例如 Anthropic 翻译出错）会在每个候选上重试一遍，白花钱。建议区分"本地异常"与"上游故障"，本地异常直接失败 |
| 中 | 同 IP 鉴权失败限流会连带影响该 IP 上的有效 key | `engine.py` `_check_auth_throttle` | 多个客户共用出口 IP 时可能误伤。建议只对"失败"计数并放宽阈值，或对已知有效 key 豁免 |
| 低 | 删除 key 后可能残留孤儿用量行 | `api_admin.delete_key` + `persist` | 先刷盘再删，但删除瞬间若有并发请求结算，下次刷盘会重新插入该 key 的 usage 行。无功能影响，只是脏数据 |
| 低 | `quota_cut` 同时会被打上 `truncated` 标记 | `outcome.py` | 两个标记语义重叠，统计时会重复计数 |
| 低 | `store.py` 里的 `try_reserve` / `settle` / `release` / `log_request` 等已被内存账本与写缓冲取代 | `store.py` | 仅测试与清理任务在用，属于死代码，建议标注或移除 |
| 低 | 每次释放并发位都创建一个 task 去通知等待者 | `quota.py` `Limiter.release` | 有轻微开销，高并发下可优化为条件变量直接通知 |
| 低 | `WriteBehind.stop()` 中 flush 失败会向上抛 | `persist.py` | 关闭阶段应吞掉异常并记日志，避免影响优雅退出 |

### 14.1 外部审计（2026-09-27，Hermes Agent 从香港探测荷兰实例）逐条回应

**前提修正**：该报告 §6.2 的历史故障 A–H 全部来自上一代 **Thalamus-Lite**，不是 v3。判据是错误原文里的 `Thalamus-Lite: all backends unavailable`、`all backends unavailable (route=code)`、`Backend 400:`、出站 UA `Thalamus-Lite/1.0` —— 这些字符串在 v3 里都不存在（v3 用 `upstream_rejected_request` / `all upstream attempts failed (client_error)`，UA 为 `thalamus-gateway/3.0`）。报告自己也注明 09-26 之前的记录指向已下线实例。

| 审计建议 | v3 状态 |
|---|---|
| ① 4xx（除 429）不计入熔断，直接透传 | **v3 已如此**：`classify_http` 把无 context/quota 字样的 400/413/422 判为 `CLIENT_ERROR`；`HealthBook.failure()` 对 `CLIENT_ERROR`/`CONTEXT_OVERFLOW` 直接 return（不计熔断、不计错误率）；`RETRYABLE` 不含 `CLIENT_ERROR`，`connect()` 立即透传上游原文 |
| ② 网关迁到香港/新加坡 | 不是代码问题。实测跨洲固定 1.28s，占端到端的绝大头，**是当前最大的单项收益**。与 EU 数据驻留的取舍见 1 节 |
| ③ reason 路由 402 无兜底 | v3 把 402 判为 `QUOTA_EXHAUSTED`（渠道级），拉黑该渠道并换家。但探测时 `/health` 显示 `channels_configured: 2` —— **有一个上游 key 没配**，兜底面比设计的窄 |
| ④ `response_format` 不被支持 → 每轮白烧 1.7s | **已改**：`ModelSpec.json_mode` 能力位 + 路由硬过滤"不支持结构化输出"，并在无候选时返回可行动的 400，不再去撞上游 |
| ⑤ HTTP keep-alive 复用 | 网关到上游本来就是长连接池 + 45 秒保温。缺的是 **nginx → 应用**（默认 HTTP/1.0，每请求重建）和 Hermes 侧客户端复用，见 `deploy/nginx.conf` |
| ⑥ 收敛上下文 / 压缩阈值 | Hermes 侧配置。`0.6 × 1M = 600K` 阈值对实测均值 65.7K 等于永不触发 |
| ⑦ 减少每回合 API 调用次数 | Agent 行为，乘法项，收益大于任何网络优化 |
| ⑧ 未知 model id 改为 4xx | **已改**：默认 `global.unknown_model: reject` → 404 并列出可用 id；要 drop-in 兼容可设 `route` |
| ⑨ `/admin` 加白名单 | **已改**：`THALAMUS_ADMIN_ALLOW`（IP/CIDR）在应用层拦，名单外一律 404；另给了 nginx 的 `allow/deny` 段。两层都有，不依赖反代配对 |
| ⑩ `reasoning_content` 回传 400 | v3 原样透传 messages，且自己的流里会输出 `reasoning_content`，客户端拿得到用于回传 —— 需要 Hermes 侧把它带回去 |
| ⑪ 出站 UA 可配 | 早已是按渠道配置项（`channels.<id>.user_agent`） |
| ⑫ 补 `/stats` | v3 从无此端点，是旧文档/脚本残留 |

另外两处报告没提但同批发现的：

- **路由耗时无法从外部测量**（报告只能用"静态地板 + 直连对照"反推，±200ms）→ 已加响应头 `X-Thalamus-Route-Ms`（= 鉴权+读体+判定+配额+打分的实际耗时），不需要 admin 权限就能把"网关开销"与"网络+上游"分开。
- **`_no_route` 的能力判定有潜在遮蔽**：只要场上有一个 pro 档模型（对 standard key 报"需要 pro 套餐"），"没有模型支持图片/结构化输出"这类可行动的 400 就会被降级成笼统的 503。已改成先剔除"这把 key 本来就用不了"的原因再判定，并补了"不支持工具调用"的专门报错。

## 16. 关键决策记录（以及被否掉的方案）

| 决策 | 理由 | 被否方案 |
|---|---|---|
| 分类不调用 LLM | 每请求多一次往返，首 token 慢 0.5–2 秒，与"快"直接冲突 | 用小模型做意图分类 |
| 统一打分公式，单位美元 | 所有取舍可比、可调、可解释 | 一串 if-else 规则 |
| 订阅用影子价格 | 不用手写"先用哪家"，额度既用满又不被闲聊提前烧光 | 固定优先级顺序 |
| 额度按钱（credits）不按 token | 同样 100 万 token，不同模型成本差 28 倍 | 按 token 限额 |
| 内存账本 + 批量写库 | 实测请求路径上的 SQLite 排队占 20ms | 每请求同步写库 |
| 首 token 后才发响应头 | 换家/对冲后模型名仍准确；失败返回正确状态码 | 先发头再流式 |
| 对冲只给便宜任务、且限成本 | Fugu 式默认多模型扇出在 €9.9 下撑不住（其隐藏 token 达可见输出 8.8 倍） | 默认多路并发 |
| 路由完全可解释、暴露实际模型 | EU AI Act 透明度 + B2B 可审计，是相对 Fugu 的差异化 | 像 Fugu 一样把路由当专有黑盒 |
| 不存 prompt，只存指纹与计量 | 隐私是产品卖点的根基 | 存原文以便复盘与训练 |
| EU-only 做溢价档不做默认档 | 欧盟拿不到订阅套利，平价档会亏重度用户 | 全量迁到欧盟托管 |
| 区域限制做成 key 级硬过滤，而不是"配置时小心" | 换家 / 对冲 / 降档有多条路径，靠人记住必然漏；硬过滤在打分前排除，路径再多也越不过去 | 只在文档里写"EU key 别配非欧渠道" |
| "只接 1M 模型"做成可校验的策略开关 | 直接删掉短窗口模型会让代码里的订阅/方言分支变成无法测试的死路；开关让门槛可调、后果在启动时可见 | 直接从 `upstreams.yaml` 删掉 200k 的 offer |
| 首 token 超时随输入长度放大 | 1M 预填充要几十秒；固定 12 秒预算会把正常长请求判成上游故障，并在每个候选上重试一遍（三倍浪费） | 统一调高所有任务的超时 |
| 先不并行，单进程 + 减少串行量 | 每请求 CPU 只 0.3ms（短）到 42ms（1M），相对上游 1–30 秒的首 token 是 1–3%；多进程要先解决 6 处进程内状态（见 7.2） | 直接开 `--workers 4` |
| 控制台加的渠道写成 `channels.d/<id>.yaml`，不改 `upstreams.yaml` | 回写主文件会冲掉里面成段的注释（定价依据、条款风险、必改项）；一渠道一文件既能自助添加，也仍然可手写、可 diff | 把渠道存数据库，或回写主 YAML |
| 上游密钥存 `data/secrets.json` 而不是数据库 | 数据库每天备份 7 份，密钥进去就等于到处都有副本；单独文件 0600 且天然不在备份里 | 存 api_keys 那张表旁边 |
| `upstreams.yaml` 里的渠道不许在控制台停用/删除 | 手写配置带注释和人工意图，控制台改了会与文件对不上；换 key 例外（运行时覆盖，不触碰文件） | 控制台可以改一切 |
| 影子价格的形状用指数、水平用对偶镜像下降学 | 这个问题在运筹学里有名字：**bid-price control**（网络收益管理，Talluri–van Ryzin 证明了渐近最优）。形状取理论最优的指数型（AdWords 的 1−1/e 结果），水平交给在线算法 —— `knee`/`full` 猜错只影响形状，价格水平由真实流量定 | 继续手调分段二次曲线的四个参数 |
| 延迟改成按任务的死线约束 | 等待效用非线性，且线性加权只能取到 Pareto 前沿凸包上的点；死线之外再退回常规打分保证不把请求判死 | 只靠 `usd_per_sec` 线性计价 |
| 重试的门槛用"失败候选自己的 σ"而不是 0 | 任务价值表只为相对排序校准，绝对值无意义（chat/1 的 score 本来就是负的）；拿 0 当门槛会让便宜任务永不重试。相对比较尺度无关 | 照 Weitzman 原式用 σ>0 |
| 验证重试放在响应开始之前，且只对面向机器消费的回答缓冲 | HTTP 头先于 body，流到一半换模型会让 `X-Thalamus-Model` 说谎；而工具调用/JSON 的客户端本来也用不了半个结果，缓冲不损体验 | 边流边验、发现不对就中断重来 |
| 不做学习型语义路由（RouteLLM 那类） | Bandits-with-Knapsacks、Weitzman 的潘多拉盒子、Chow's rule 这些定理都要求**可观测的奖励**，而产品承诺不存 prompt、现有信号只有稀疏负反馈。这是信息论约束，不是算法能绕过的 —— 先造验证器才能解锁 | 直接上 embedding + 分类器 |
| 影子价格加"单次占比"项，而不是把 knee 调低 | 调低 knee 会让所有请求都提早涨价，浪费额度；问题只出在"单次就很大"的请求上，就只对它加价 | 把 `knee` 从 0.5 降到 0.15 |
| 客户端没给 `max_tokens` 时不替它设 | 替它设会改变上游默认行为（有些模型据此决定思考预算）；只在客户端给了值时用剩余窗口夹住 | 总是把 `max_tokens` 设成剩余空间 |
